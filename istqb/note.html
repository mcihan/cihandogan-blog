    Test nesnesi nedir?

    Syllabus §1.1 · FL-1.1.1 · test object

    Tek cümle

    Test nesnesi = test ettiğin şey. Syllabus'un ifadesiyle: yazılım geliştirme sırasında üretilen iş ürünlerine, test edilirken test nesnesi adı verilir.

    Üç örnek

    1 — Giriş ekranı. Şifre giriş ekranını açtın, farklı şifreler deniyorsun.
    Test nesnesi: giriş ekranı

    2 — Aynı ekran, ama henüz kod yok. Giriş ekranının gereksinim dokümanını okuyorsun, “burada şifre uzunluğu yazmamış” diyorsun.
    Test nesnesi: gereksinim dokümanı

    Kod çalıştırmadın ama yine test ettin (statik test). Yani test nesnesi illa çalışan yazılım değil — doküman da olabilir.

    3 — Tek bir fonksiyon. hesaplaKdv() metoduna birim testi yazdın.
    Test nesnesi: o metot

    Karışan yer: test esası

    İkisi aynı anda var ve farklı şeyler:

    “Gereksinim dokümanına bakarak giriş ekranını test ediyorum.”

    • test nesnesi → giriş ekranı (test ettiğim)
    • test esası → gereksinim dokümanı (baktığım kaynak)

    Ama 2. örnekte dokümanın kendisini inceliyordum — orada doküman test nesnesi olmuştu. Aynı şey, rolüne göre ikisinden biri olabilir.

    Ayırt etme sorusu

    “Hata bulursam kimde hata var?”
    Giriş ekranında → nesne giriş ekranı. Dokümanda → nesne doküman.

    Sınavda nerede karşına çıkar

    Doğrudan “test nesnesi nedir” diye sorulmaz; şıklarda ayırt edici olarak kullanılır. §2.2.1'de test seviyelerini birbirinden ayıran beş ölçütten biridir (test nesnesi, test hedefleri, test esası, hatalar/arızalar, yaklaşım ve sorumluluklar). §4.1'de kara kutu, test nesnesinin iç yapısına bakmadan davranışını analiz eder. §5.5'te hata raporunda bulunması gereken alanlardan biridir.

    İnsan hatası, hata, arıza, kök neden

    Syllabus §1.2.3 · FL-1.2.3 · error / defect / failure / root cause
    kök neden→insan hatası→ hata→arıza

    Tek örnek üzerinden

    Bir e-ticaret sitesinde “500 TL üzeri siparişlerde %10 indirim” kuralı var. Geliştirici yorgun, gece 11'de kod yazıyor ve şunu yazıyor:

    if (tutar > 500) indirimUygula();   // olması gereken: >= 500
    TerimBu örnekteNerede yaşar
    İnsan hatası
    error    		 Geliştiricinin >= yerine > yazması İnsanın kafasında / elinde
    Hata
    defect, bug    		 Koddaki o > işareti Üründe durur — kimse çalıştırmasa da oradadır
    Arıza
    failure    		 Müşteri tam 500 TL'lik sipariş veriyor, indirim uygulanmıyor Çalışma anında gözlemlenen yanlış davranış
    Kök neden
    root cause    		 Gece mesaisi / acele / kod gözden geçirme yapılmaması Problemin asıl sebebi

    Üç kritik nokta

    1. Her hata arızaya dönüşmez. Yukarıdaki hata, 500 TL'lik sipariş gelmezse hiç görünmez. 499 veya 501 TL'lik siparişlerde her şey doğru çalışır. Hata hep orada, ama arıza yok.

    2. Her arızanın arkasında hata olmayabilir. Sunucuya yıldırım düşüyor, bellek bozuluyor, sistem yanlış sonuç veriyor. Arıza var, kodda hata yok. Syllabus bunu açıkça söylüyor: arızalar radyasyon, elektromanyetik alan gibi çevresel koşullardan da olabilir.

    3. Hata sadece kodda olmaz. Analist gereksinim dokümanına “500 TL üzeri” yazdıysa ama iş birimi “500 dahil” demek istediyse → hata dokümanda. Geliştirici kodu dokümana göre doğru yazmış olsa bile ürün yanlış.

    Sınavda nasıl sorulur

    Sana bir senaryo verilir, hangisinin ne olduğunu işaretlersin:

    İfadeCevap
    “Test uzmanı, 500 TL'lik siparişte indirimin uygulanmadığını gözlemledi.” arıza
    “İnceleme sonucu koşulun > yerine >= olması gerektiği görüldü.” hata
    “Geliştirici, kuralı yanlış anlamıştı.” insan hatası

    Pratik ayırt etme

    • Gördüğün şey → arıza (dışarıdan belli)
    • Bulduğun şey → hata (içeri bakınca belli)
    • Yapan şey → insan hatası

    Ayrıca

    Hata ayıklama (debugging) test değildir. Test arızayı tetikler; sonra geliştirici hata ayıklama yaparak o arızanın arkasındaki hatayı bulur ve düzeltir. Hata ayıklama adımları: arızayı yeniden oluşturma → teşhis → düzeltme. Ardından onaylama testi düzeltmenin işe yarayıp yaramadığını kontrol eder (§1.1.2).
